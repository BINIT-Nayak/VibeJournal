# VibeJournal engineering review

Review scope: application routes, auth/session and account flows, journal persistence/sync/encryption, analytics/dashboard queries, AI/music boundaries, client composition, dependencies, and test/CI structure. Priorities below reflect concrete code paths, not a claim of penetration testing or load profiling.

## Prioritized findings

1. **P1 · Fixed — Account changes are not atomic or protected against stale verification.** `src/server/auth/routes/settings/route.ts` verifies a password, then later updates by user ID only. A concurrent reset/change can be overwritten. Settings commit before the user update, so duplicate-email failures can leave AI consent changed. Password changes revoke sessions separately and leave outstanding reset tokens usable. Fix with one transaction and a conditional credential write; remove reset tokens and sessions in the same transaction.
2. **P1 · Fixed — Email changes bypass re-authentication; password verification lacks throttling.** The settings endpoint accepts email changes with only an existing session, and repeated password guesses bypass the login limiter. Add bounded input validation, current-password verification for changed email, a durable per-user account-change limit, and reject OAuth email changes until a verified linking flow exists. Keep name/theme/preferences usable without re-authentication.
3. **P2 · Fixed — Login unnecessarily decrypts all journals.** `currentUserPayload` calls unbounded `listEntries`, and login invokes it after successful authentication. Large histories amplify database/key access; an unavailable content key incorrectly turns valid login into a 503. Return identity/settings only during login. Preserve the legacy current-user/history response until its profile consumer is migrated.
4. **P2 · Fixed — Sync updates clear omitted tags.** `journal-sync/service.ts` converted an omitted optional tags field to an empty list, whereas the regular update service preserves omitted fields. Preserve `undefined` for updates and use an empty default only for creates. A PostgreSQL regression checks encrypted tag preservation, explicit clearing, and idempotent replay.
5. **P2 — Settings/profile still downloads all history.** `/api/auth/me`, `/api/entries`, and `VibeJournalApp`'s profile path load and decrypt the entire history. Profile statistics are recomputed in the browser. Follow up with a structured profile aggregate endpoint and migrate this consumer before removing legacy APIs. The canonical journal history already uses cursor pagination.
6. **P2 — Cache invalidation can be lost during a Redis outage.** Analytics generation tokens exist only in Redis. A write while Redis is unavailable can leave previously cached data readable after recovery until its five-minute TTL. Use a durable journal revision in cache keys if immediate cross-instance freshness is required. Existing compare-and-set protects successful invalidation races but not lost invalidations.
7. **P2 · Fixed — Error mappings drift across endpoints.** Weekly reflection maps invalid-origin failures and malformed JSON to 503 instead of 403/400. This misleads clients and observability. Fix this mapping locally; avoid replacing all stable response contracts at once.
8. **P2 — Production password-reset delivery is incomplete.** Reset requests create tokens, but only development returns a token; no production mail delivery is wired up. Production responds with success without delivering a reset. Requires a chosen delivery service and verified account/email-change workflow; do not expose production reset tokens to compensate.
9. **P3 — Legacy client shell and parallel APIs complicate maintenance.** `VibeJournalApp` still contains hash-based screens beside App Router pages; sync and regular journal services duplicate parts of encryption/tag/update orchestration. Retain sync's atomic receipt/conflict semantics. Consolidate small validated mutation preparation only when changing those flows, rather than introducing a generic domain framework now.
10. **P3 — Query and storage growth need measured follow-up.** Tag writes use sequential upserts/inserts (bounded at 20); decryption checks wrapped-key rows for each field/tag; exports materialize a full snapshot; sync receipts and reset/rate-limit rows need a retention policy. Measure realistic high-volume fixtures before batching or caching authorization/key reads. Avoid deleting receipts without preserving idempotency guarantees.
11. **P3 — Provider abstraction leaks vendor presentation.** Music service accepts an injected provider but hardcodes `provider: "iTunes"` and catalog-specific explanatory text. Move display metadata into provider results when adding another provider; no additional adapter framework is needed today.

## Boundaries that should stay

Journal reads/writes are owner-scoped, optimistic updates include ownership/version in the write predicate, SQL analytics use bound parameters and structured columns, AI calls recheck consent/ownership, and encryption uses authenticated context. Client feature/components have no direct server or Prisma imports. Executable server boundaries use `server-only` (the pure env/audit schemas and static route constants intentionally do not); domain contracts live in shared feature modules. Charts and interaction-heavy forms justify client components; the old shell is the larger compositional concern. A production client-chunk marker scan found no Prisma client, KMS SDK, or private environment-variable names. This is corroborating evidence, not a proof against every possible bundle leak. Of 63 TSX modules, 31 declare `use client`; counting alone is not a reason to convert interactive components. Existing dependencies serve implemented features; no dependency removal is justified solely by package size without bundle measurements.

## Verification and limits

Validation: 34 unit/UI tests and seven PostgreSQL integration tests passed, along with the auth, journal CRUD, and mood-trend API suites. Lint, formatting, strict TypeScript checking, and the production build passed. All seven browser journeys passed with source edits stopped, including the new email re-authentication flow. An earlier run had one edit-navigation timeout during ongoing development rebuilds; six journeys passed in that run. The clean rerun passed without increasing timeouts or adding retries. The login response retains an empty `entries` compatibility field; actual history remains available through the existing authenticated endpoints. This review does not certify external AWS/vendor configuration, hosting access logs, production email delivery, or production query latency. Remaining items above are explicit follow-ups, not silently fixed by refactoring.
