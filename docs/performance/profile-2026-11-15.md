# VibeJournal performance profile — 15 November 2026

## Method and limits

Measured Next.js 15.5.29 production builds (`next build`, `next start`), local PostgreSQL, and headless desktop Chrome. Three fresh browser contexts per route; no CPU/network throttling. SQL events record only table names and integer-millisecond durations, never SQL, parameters, journal text, credentials, or keys. Request measurements run sequentially on an isolated port with no browser prefetch. SQL counts include transaction-control statements.

The local development encryption key is correctly unavailable in production. Dashboard, Settings, Music, and Journal page-load measurements therefore use an empty disposable account. Analytics queries use 90 synthetic structured-only rows (no tags); their opaque test payload is never decrypted. Those rows are removed before browser tests. The browser replays the measured 7/30/90-day analytics responses to isolate chart work from server/cache timing. No production encryption safeguards were changed. Redis is disabled only for the profiling server to measure uncached SQL consistently.

This is not a production load test or a claim about field Core Web Vitals. Production KMS latency, populated Settings/history decryption, tag-heavy data, large accounts, slow devices, and external music-provider latency remain unmeasured. Timing samples are small and sensitive to local machine activity; byte counts and SQL counts are the stronger findings. Regression tests ran separately against the development server (some overlapped the after-profile run), so timing changes should not be interpreted as isolated causal improvements.

Raw measurements: [before](./before.json), [after](./after.json). No account identifiers or journal contents are included.

### Inactive client screens and bundles

`VibeJournalApp` eagerly imported the editor, new-entry page, legacy journal/music screens, analytics, and Settings even when showing Dashboard. These interactive screens remain client components, but now load through `next/dynamic` only when selected. Loading announcements preserve feedback during chunk loading. Existing hash routes remain supported.

Recharts was also downloaded for an empty mood chart. The SVG plot is now a separate dynamically loaded component, rendered only when there are mood values. Empty states, descriptions, chart dimensions, and the accessible table remain in the small wrapper. The Recharts-containing production chunk is approximately 112 kB gzip; Dexie is approximately 31 kB gzip. Dexie remains available for required drafts/sync behavior. Framework chunks were not rewritten or replaced.

No broad conversion of interactive forms, navigation, query consumers, or offline components to server components was justified. Static presentation imported through client trees (for example, the auth layout) remains a possible future boundary refinement, not an established bottleneck from these measurements.

### Duplicate database work

Root layout, journal layout, and page independently called `getCurrentUser()`. React's request/render-scoped `cache()` now shares that lookup during server rendering; it does not cache sessions across users or requests. Additionally, Auth.js already reads the persisted session and its user, validates expiry and credential version, and derives the public session from that database record. A second `user.findUnique` immediately afterward was redundant and is removed.

Protected routes still perform server-side session/user validation. API calls remain independently authenticated. Authentication regression tests verify forged updates, cross-user ownership, logout replay, password changes, account deletion, and expiration.

No identical duplicate HTTP fetch appeared during the recorded page loads. Dashboard made one dashboard request and one music-source request; Settings made dashboard, current-user/history, and music-preferences requests. The latter have overlapping data, and Settings' full-history load deserves a populated-account profile, but this run does not measure its encrypted-data cost. No speculative API consolidation or cache policy change was made.

### Database operations

With 90 structured rows, uncached analytics returned in 12–29 ms before and 15–27 ms after. Most individual SQL timings were 0–2 ms; the largest observed statement was 11 ms before and 9 ms after. Zero means below the profiler's integer-ms resolution. These samples do not establish a slow query or justify new indexes, transaction changes, or repository rewrites. Existing user/date indexes remain unchanged. The query-count improvement is reliable; an endpoint-latency improvement is not established.

### Charts

Measured 7-day and 90-day changes used 32/25 ms of browser task time before and 24/22 ms after, including React updates and measurement overhead, not just pure chart render time. SVG descendant counts remained 86/197; chart-size warnings were zero. Existing disabled line animation, gaps for missing days, responsive sizing, and data tables are preserved. There is no evidence here for downsampling, replacing Recharts, or adding render memoization.

Median initial browser task time for populated Analytics increased from 97 ms to 123 ms in these samples. Conditional chart loading introduces an additional chunk/render step; it benefits empty states and routes without charts, not populated chart startup. No overall Analytics speedup is claimed.

## Verification

- Production build, TypeScript/build validation, ESLint, Stylelint, and formatting checks passed.
- Authentication regression suite passed, including session revocation and ownership.
- Browser profiling completed across five routes, three runs each, plus 7/90-day chart changes.
- Accessibility regression suite passed all 16 page/state checks on an isolated rerun, covering forms, protected screens, dialogs, theme, mobile navigation, mood selection, and chart alternatives. The first run timed out awaiting the account-deletion password field; that timeout did not reproduce in isolation.

## Reproduce

Use a local test database with current migrations, configured app environment, and Chrome installed. The script creates and deletes only its disposable account and fixture rows. Avoid concurrent test traffic when comparing timings. Do not use a production database.

```sh
npm run build
PLAYWRIGHT_MODULE=/absolute/path/to/playwright PROFILE_OUTPUT=/tmp/vibejournal-profile.json node scripts/profile-app.mjs
```

`PLAYWRIGHT_MODULE` can be omitted when Playwright is locally resolvable. `PROFILE_PORT` defaults to 3100. The script starts/stops its own production server. `PROFILE_DATABASE=1` enables the privacy-limited SQL instrumentation; it is otherwise disabled. Keep the same browser, fixture size, machine conditions, and build mode for comparisons.
